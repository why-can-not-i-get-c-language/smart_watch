- 列表显示设备名、完整地址、RSSI和最近发现时间，以地址合并同一设备。名称优先取非空`ScanRecord.deviceName`，再使用设备缓存名；后续广播带来名称时更新旧行，空名称不覆盖已有有效名称。

**通知兼容。** 本台模块DFB1、DFB2均显示Notify/Read/Write/Write No Response，服务发现未提供CCCD `0x2902`；nRF Connect开启通知失败。原厂BlunoBasicDemo已实测收到手表回显及主动发送，手机端需适配该模块的接收流程。

手机端对照原厂[串口回显示例](https://wiki.dfrobot.com/tel0073/docs/22558)及本仓库[BlunoLibrary.java正文](references/text/26_BLE_官方Android示例_BlunoLibrary.java.txt)、[BluetoothLeService.java正文](references/text/26_BLE_官方Android示例_BluetoothLeService.java.txt)，核对命令通道初始化并实现DFB1本地通知监听。原厂示例调用`setCharacteristicNotification`，CCCD写入代码被注释；通过实测确定所需初始化步骤，不直接照搬示例中的密码和波特率写入。存在2902时走标准订阅，缺失时走兼容流程。初始化读写按回调顺序执行，保持现有模块密码、波特率及固件版本；本地监听返回成功或服务发现成功均不能单独作为“可收发”的依据。

**字节与队列。** 收发使用原始ByteArray，接收入口为`onCharacteristicChanged`，按原字节处理并保留00/FF/CR/LF。发送串行排队，单次写入长度与分片依据实际能力确定。P01按回调顺序累计原始字节，不添加业务帧；APP-03冻结后再按协议组帧，支持跨通知分片及同次通知中的多帧。分别记录提交发送、GATT写入完成和实际回显。

**临时调试入口。** 在现有设备详情页提供HEX输入及单次发送、HEX接收内容/长度/时间、本次连接累计收发字节数、清空及复制记录、初始化失败阶段与错误提示。重连后区分历史与本次数据；调试入口可在正式版本隐藏，但实际收发及错误反馈须保留。

#### 公共帧

以下多字节整数均为无符号、小端；不直接序列化C结构体，不依赖padding。帧头不转义，依长度与CRC定位。DFB1承载数据，Android当前17字节写入分片与手表16字节UART读取均只作传输块，均不代表帧边界。

| 帧偏移 | 字段 | 宽度 | 取值与解释 |
| --- | --- | --- | --- |
| 0 | magic | 2 | 固定A5 5A |
| 2 | version | 1 | 01；不同布局版本不兼容 |
| 3 | kind | 1 | 00请求，01应答；本轮无主动业务事件 |
| 4 | cmd | 1 | 01 DeviceInfo，02 GetStatus，03 SetTime |
| 5 | sequence | 2 | 1..65535，同一session内严格递增；应答原样关联 |
| 7 | session | 4 | 手机选择的非零会话标识；应答原样关联，不是密钥或认证 |
| 11 | payload_length N | 2 | 0..128，仅载荷长度 |
| 13 | payload | N | 按下表定义 |
| 13+N | crc32 | 4 | 覆盖帧偏移0..12+N，共13+N字节；CRC本身不参与 |

帧总长为 `17 + N` 字节，`N` 为载荷长度。13 字节帧头、最多 128 字节载荷与 4 字节 CRC 合计最多 **145 字节**。CRC采用现有`code/System/crc32.c`：反射多项式0xEDB88320，init/xorout均0xFFFFFFFF；校验向量ASCII 123456789→0xCBF43926，线上尾部26 39 F4 CB。CRC只查传输完整性，不提供配对、身份认证或授权。首轮为受控台架单手机通信，产品访问控制另行确认。

接收按字节推进并有界保留至多 145 字节的候选帧：搜索A5 5A，读满13字节头后核对版本/kind/长度，再等待17+N字节；CRC通过才分派，随后继续处理剩余字节，故支持跨多次接收的一帧及一次接收多帧。长度超过128、版本非01或CRC错误，从当前候选起丢1字节后重新找帧头，不信任坏帧的长度跳过后续好帧；CRC错误及未知布局版本均静默丢弃、不发失败回包。尾部单独A5保留等待后续。候选帧字节间隔超过1000ms或从帧头起超过5000ms则废弃并继续找下一候选；UART溢出/错误须使当前候选失效并记诊断，不把残缺帧交业务。精确计时、流控及缓冲峰值均需后续软件测试验证。

应答必须经过统一发送队列按不大于16字节推进，至多每5ms发送一次，禁止业务函数各自抢UART。发送失败不盲目重发半帧，手机按完整应答超时处理。手机也串行排队写入，连接未就绪时不发送；在应用层同时只保留一个未完成请求。

#### 会话、超时、重复请求和错误

手机首先用新非零session、seq=1发空载荷DeviceInfo，只有收到成功应答后才发其他命令；新session的合法DeviceInfo建立/替换当前会话，其他未知session请求返回04 NOT_READY。新 session 的 DeviceInfo 必须使用 seq=1；其他非零 seq 返回 02。seq=0或session=0返回02 BAD_VALUE，不建立会话。错误应答沿用请求cmd、sequence、session，kind=01、version=01；不以请求kind=01生成应答。

同一 session 每个新请求使用更大的 seq，达到 65535 后用新 session。手表开始执行前记录 session、seq 和完整请求。完成副作用与读回后，先缓存完整请求和应答（含已受理请求的失败），再发送。最后一个已完成应答缓存 30 秒。缓存过期时保留最高 seq，原样重发的该 seq 返回 08；最后已完成的同 seq 不同字节返回 07。收到已受理的更大 seq 后，旧 seq 返回 08。

执行中先区分 session，再比较 seq，最后比较完整请求。以下规则针对帧结构及 CRC 已通过且 session/seq 非零的请求：

| 条件 | 应答及去重状态 |
| --- | --- |
| 当前 session、同 seq、完整字节相同 | 合并到原执行。执行完成后发送原事务的最终应答。 |
| 当前 session、同 seq、完整字节不同 | 返回 07 SEQ_CONFLICT。 |
| 当前 session、seq 比正在执行的 seq 小 | 返回 08 REQUEST_EXPIRED。 |
| 当前 session、seq 更大，或新 session 的合法空载荷 DeviceInfo（seq=1） | 返回 06 BUSY。新会话等原执行完成后再建立。 |
| 其他 session 的请求 | 返回 04 NOT_READY。 |

执行期的临时 04/06/07/08 通过统一发送队列发送，保留正在执行的请求及其最终应答缓存位置。06 不消耗被拒绝的 seq，也不切换会话。手机收到 06 后按错误码表处理。

手机先登记预期的连接、cmd/session/seq，再提交首个分片，避免漏掉早于末次写回调到达的合法应答。写回调仅表示传输进度；本次尝试尚未收到应答时，从最后一个分片的成功写回调开始等待完整、CRC正确且cmd/session/seq匹配的应答，超时2000ms；同一连接内最多重试2次（总计3次），重试必须使用同session、同seq及完全相同字节，不重取时间。GATT 写入本身必须有独立的失败或超时出口；部分写入或写回调丢失时，撤销该次事务，按下节等待残帧失效后再建立新会话并先查状态。手机的整次操作时限应容纳分片写入、各次应答窗口和单独的读回事务。设备执行时间目标小于应答超时，另经实测确认。缓存应答中的时间是原执行时回读值，重试回包不能当作新采样；手机另发新seq GetStatus查看当前时间。连接断开立即停止重试并撤销就绪；重连后新session执行DeviceInfo→GetStatus，若仍需校时，用新seq和手机当前时间重新发SetTime，不自动续发断线前的写请求。设备复位后RAM去重状态丢失，不承诺跨复位exactly-once；不得因此把旧SetTime自动补发。session不是链路状态检测或多客户端访问控制。

#### 半帧恢复

- 两端以单调时钟记录候选的首字节和最近一次加入的字节。字节间隔超过 1000 ms 或候选年龄超过 5000 ms 时丢弃未完成候选，包括单独的 A5。每次送入新字节前先做过期检查；固件可在周期任务中额外检查。手表不能依赖 BLE 断开通知重置 UART 缓冲。
- 手机提交了部分分片、GATT 写入结果不确定，或带未完成事务断线时，停止旧 GATT 队列并关闭旧连接，丢弃本地候选和旧连接回调。新连接完成服务发现和订阅后，首个 DeviceInfo 还需等恢复时间：从旧链路最后可能向手表递交字节的时刻起，连续静默超过 1000 ms，或已确认旧候选超过 5000 ms 且旧字节已停止到达。手机无法直接观测手表 UART，首轮台架保守实现为新连接准备好后等待 5500 ms 再发首帧，期间不提交业务或调试字节。用固件 UART 记录验证模块的尾部字节在此窗口内已排尽、候选已清；若仍有晚到字节，先核实模块队列上界再调整等待，保留失败提示。
- 若请求已完整发送，同一连接只收到部分应答，先按 2000 ms 应答超时判断本次尝试，再等本地不完整候选过期，随后用原 session、seq 及字节重传；如期间收到匹配的完整应答，停止重传。手表开始发送前已缓存完整应答；半途发送失败时结束原发送，等待手机的完整请求再从帧头重放缓存。上次应答残留尚未排尽或缓存已过期时，按发送队列或 08 路径处理。

成功应答载荷第0字节为00，并附命令数据；失败应答载荷只含1字节错误码，不附看似有效的数据。线上的错误码独立定义，不能直接强转watch_status_t：

| 错误码 | 含义与手机动作 |
| --- | --- |
| 00 | OK；仍按命令检查长度及字段有效性 |
| 01 | BAD_LENGTH：命令载荷长度不符，修正请求 |
| 02 | BAD_VALUE：时间越界、零session/seq等，修正参数 |
| 03 | UNSUPPORTED：CRC正确、版本01但命令不支持，停止调用 |
| 04 | NOT_READY：会话或RTC未就绪，重新查询/初始化，不假报成功 |
| 05 | IO_ERROR：RTC/驱动读写失败，查询状态后由用户决定重试 |
| 06 | BUSY：本次未执行，稍后使用新seq，写请求须先查状态 |
| 07 | SEQ_CONFLICT：相同seq不同内容，修正请求序号 |
| 08 | REQUEST_EXPIRED：旧请求或重放缓存过期，先查询再发新请求 |
| 09 | INTERNAL：内部状态/编码异常，保留失败状态并诊断 |
| 0A | TIMEOUT：底层操作超时，先查询当前状态，不能推定没发生副作用 |

参数错误不触碰RTC；若写入后回读失败，只返回相应错误，手机必须认为结果未知并查询，不能假定RTC未改变。WATCH_OK→00、INVALID_ARGUMENT→02、NOT_IMPLEMENTED→03、NOT_READY→04、IO_ERROR→05、TIMEOUT→0A、INVALID_DATA→05；其他内部错误→09。帧CRC失败不返回上述错误码。

#### 校时读回与验收计时

1. 手机在首次提交 SetTime 首个分片前取当前 UTC 整秒填入请求，同时记单调时刻 `t0`。收到并验完匹配的完整 SetTime 应答时记 `t1`。同一请求重传沿用原来的字节和 `t0`。固件回读为请求秒或下一秒均可接受。这里的 1000 ms 用于判定测量条件，2000 ms 用于决定一次应答等待是否超时。
2. 收到合法成功应答后，立即用新 seq 发 GetStatus。这个请求也分别记录首次提交首个分片前的 `t2` 和收到并验完完整匹配应答的 `t3`，在 `t3` 同时读取手机当前 UTC 整秒。两段耗时都使用同一部手机的单调时钟。两段均无重传、`t1 − t0 ≤ 1000 ms`、`t3 − t2 ≤ 1000 ms`、手机期间无系统时间跳变，才进入短时精度判断。
3. 判为“校时已验证”须同时满足上面的计时条件、SetTime 回读合格、GetStatus 的 `time_state=02`，且 `abs(手表快照 UTC − 手机在 t3 的 UTC) ≤ 2 秒`。两边都按 UTC 秒比较，包括北京时间跨日的情况。若条件合格而差值超限，显示读回偏差并保留两端值。
4. 若超出低延迟窗口或发生重传，记录“延迟过大／待复核”。写后超时、IO_ERROR、回读不合法或断线，记录“校时结果待确认”。连接就绪后先用新 seq 查询当前时间；断线时先建新 session。仅当新查询表明仍需校时，才用当前时间发起新 SetTime。若查询已吻合，可显示“当前时间已核对”，保留原校时尝试的未确认或超窗口状态。
