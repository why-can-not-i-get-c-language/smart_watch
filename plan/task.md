### APP-03 现行D3基础协议

#### 公共帧

以下多字节整数均为无符号、小端；不直接序列化C结构体，不依赖padding。帧头不转义，依长度与CRC定位。DFB1承载数据，Android当前17字节写入分片与手表16字节UART读取均只作传输块，均不代表帧边界。

| 帧偏移 | 字段 | 宽度 | 取值与解释 |
| --- | --- | --- | --- |
| 0 | magic | 2 | 固定A5 5A |
| 2 | version | 1 | 01；不同布局版本不兼容 |
| 3 | kind | 1 | 00请求，01应答；本轮无主动业务事件 |
| 4 | cmd | 1 | 01 DeviceInfo，02 GetStatus，03 SetTime |
| 5 | sequence | 2 | 1..65535，同一session内严格递增；应答原样关联 |
| 7 | session | 4 | 手机选择的非零会话标识；应答原样关联，不是密钥或认证 |
| 11 | payload_length N | 2 | 0..128，仅载荷长度 |
| 13 | payload | N | 按下表定义 |
| 13+N | crc32 | 4 | 覆盖帧偏移0..12+N，共13+N字节；CRC本身不参与 |

帧总长为 `17 + N` 字节，`N` 为载荷长度。13 字节帧头、最多 128 字节载荷与 4 字节 CRC 合计最多 **145 字节**。CRC采用现有`code/System/crc32.c`：反射多项式0xEDB88320，init/xorout均0xFFFFFFFF；校验向量ASCII 123456789→0xCBF43926，线上尾部26 39 F4 CB。CRC只查传输完整性，不提供配对、身份认证或授权。首轮为受控台架单手机通信，产品访问控制另行确认。

接收按字节推进并有界保留至多 145 字节的候选帧：搜索A5 5A，读满13字节头后核对版本/kind/长度，再等待17+N字节；CRC通过才分派，随后继续处理剩余字节，故支持跨多次接收的一帧及一次接收多帧。长度超过128、版本非01或CRC错误，从当前候选起丢1字节后重新找帧头，不信任坏帧的长度跳过后续好帧；CRC错误及未知布局版本均静默丢弃、不发失败回包。尾部单独A5保留等待后续。候选帧字节间隔超过1000ms或从帧头起超过5000ms则废弃并继续找下一候选；UART溢出/错误须使当前候选失效并记诊断，不把残缺帧交业务。已执行的软件检查及尚未量化的真实时序、流控和峰值边界见F06.md。

应答必须经过统一发送队列按不大于16字节推进，至多每5ms发送一次，禁止业务函数各自抢UART。发送失败不盲目重发半帧，手机按完整应答超时处理。手机也串行排队写入，连接未就绪时不发送；在应用层同时只保留一个未完成请求。

#### 会话、超时、重复请求和错误

手机首先用新非零session、seq=1发空载荷DeviceInfo，只有收到成功应答后才发其他命令；新session的合法DeviceInfo建立/替换当前会话，其他未知session请求返回04 NOT_READY。新 session 的 DeviceInfo 必须使用 seq=1；其他非零 seq 返回 02。seq=0或session=0返回02 BAD_VALUE，不建立会话。错误应答沿用请求cmd、sequence、session，kind=01、version=01；不以请求kind=01生成应答。

同一 session 每个新请求使用更大的 seq，达到 65535 后用新 session。手表开始执行前记录 session、seq 和完整请求。完成副作用与读回后，先缓存完整请求和应答（含已受理请求的失败），再发送。最后一个已完成应答缓存 30 秒。缓存过期时保留最高 seq，原样重发的该 seq 返回 08；最后已完成的同 seq 不同字节返回 07。收到已受理的更大 seq 后，旧 seq 返回 08。

执行中先区分 session，再比较 seq，最后比较完整请求。以下规则针对帧结构及 CRC 已通过且 session/seq 非零的请求：

| 条件 | 应答及去重状态 |
| --- | --- |
| 当前 session、同 seq、完整字节相同 | 合并到原执行。执行完成后发送原事务的最终应答。 |
| 当前 session、同 seq、完整字节不同 | 返回 07 SEQ_CONFLICT。 |
| 当前 session、seq 比正在执行的 seq 小 | 返回 08 REQUEST_EXPIRED。 |
| 当前 session、seq 更大，或新 session 的合法空载荷 DeviceInfo（seq=1） | 返回 06 BUSY。新会话等原执行完成后再建立。 |
| 其他 session 的请求 | 返回 04 NOT_READY。 |

执行期的临时 04/06/07/08 通过统一发送队列发送，保留正在执行的请求及其最终应答缓存位置。06 不消耗被拒绝的 seq，也不切换会话。手机收到 06 后按错误码表处理。

手机先登记预期的连接、cmd/session/seq，再提交首个分片，避免漏掉早于末次写回调到达的合法应答。写回调仅表示传输进度；本次尝试尚未收到应答时，从最后一个分片的成功写回调开始等待完整、CRC正确且cmd/session/seq匹配的应答，超时2000ms；同一连接内最多重试2次（总计3次），重试必须使用同session、同seq及完全相同字节，不重取时间。GATT 写入本身必须有独立的失败或超时出口；部分写入或写回调丢失时，撤销该次事务，按下节等待残帧失效后再建立新会话并先查状态。手机的整次操作时限应容纳分片写入、各次应答窗口和单独的读回事务。设备执行时间目标小于应答超时，另经实测确认。缓存应答中的时间是原执行时回读值，重试回包不能当作新采样；手机另发新seq GetStatus查看当前时间。连接断开立即停止重试并撤销就绪；重连后新session执行DeviceInfo→GetStatus，若仍需校时，用新seq和手机当前时间重新发SetTime，不自动续发断线前的写请求。设备复位后RAM去重状态丢失，不承诺跨复位exactly-once；不得因此把旧SetTime自动补发。session不是链路状态检测或多客户端访问控制。

#### 半帧恢复

- 两端以单调时钟记录候选的首字节和最近一次加入的字节。字节间隔超过 1000 ms 或候选年龄超过 5000 ms 时丢弃未完成候选，包括单独的 A5。每次送入新字节前先做过期检查；固件可在周期任务中额外检查。手表不能依赖 BLE 断开通知重置 UART 缓冲。
- 手机提交了部分分片、GATT 写入结果不确定，或带未完成事务断线时，停止旧 GATT 队列并关闭旧连接，丢弃本地候选和旧连接回调。新连接完成服务发现和订阅后，首个 DeviceInfo 还需等恢复时间：从旧链路最后可能向手表递交字节的时刻起，连续静默超过 1000 ms，或已确认旧候选超过 5000 ms 且旧字节已停止到达。手机无法直接观测手表 UART，首轮台架保守实现为新连接准备好后等待 5500 ms 再发首帧，期间不提交业务或调试字节。用固件 UART 记录验证模块的尾部字节在此窗口内已排尽、候选已清；若仍有晚到字节，先核实模块队列上界再调整等待，保留失败提示。
- 若请求已完整发送，同一连接只收到部分应答，先按 2000 ms 应答超时判断本次尝试，再等本地不完整候选过期，随后用原 session、seq 及字节重传；如期间收到匹配的完整应答，停止重传。手表开始发送前已缓存完整应答；半途发送失败时结束原发送，等待手机的完整请求再从帧头重放缓存。上次应答残留尚未排尽或缓存已过期时，按发送队列或 08 路径处理。

成功应答载荷第0字节为00，并附命令数据；失败应答载荷只含1字节错误码，不附看似有效的数据。线上的错误码独立定义，不能直接强转watch_status_t：

| 错误码 | 含义与手机动作 |
| --- | --- |
| 00 | OK；仍按命令检查长度及字段有效性 |
| 01 | BAD_LENGTH：命令载荷长度不符，修正请求 |
| 02 | BAD_VALUE：时间越界、零session/seq等，修正参数 |
| 03 | UNSUPPORTED：CRC正确、版本01但命令不支持，停止调用 |
| 04 | NOT_READY：会话或RTC未就绪，重新查询/初始化，不假报成功 |
| 05 | IO_ERROR：RTC/驱动读写失败，查询状态后由用户决定重试 |
| 06 | BUSY：本次未执行，稍后使用新seq，写请求须先查状态 |
| 07 | SEQ_CONFLICT：相同seq不同内容，修正请求序号 |
| 08 | REQUEST_EXPIRED：旧请求或重放缓存过期，先查询再发新请求 |
| 09 | INTERNAL：内部状态/编码异常，保留失败状态并诊断 |
| 0A | TIMEOUT：底层操作超时，先查询当前状态，不能推定没发生副作用 |

参数错误不触碰RTC；若写入后回读失败，只返回相应错误，手机必须认为结果未知并查询，不能假定RTC未改变。WATCH_OK→00、INVALID_ARGUMENT→02、NOT_IMPLEMENTED→03、NOT_READY→04、IO_ERROR→05、TIMEOUT→0A、INVALID_DATA→05；其他内部错误→09。帧CRC失败不返回上述错误码。

#### 校时读回与验收计时

1. 手机在首次提交 SetTime 首个分片前取当前 UTC 整秒填入请求，同时记单调时刻 `t0`。收到并验完匹配的完整 SetTime 应答时记 `t1`。同一请求重传沿用原来的字节和 `t0`。固件回读为请求秒或下一秒均可接受。这里的 1000 ms 用于判定测量条件，2000 ms 用于决定一次应答等待是否超时。
2. 收到合法成功应答后，立即用新 seq 发 GetStatus。这个请求也分别记录首次提交首个分片前的 `t2` 和收到并验完完整匹配应答的 `t3`，在 `t3` 同时读取手机当前 UTC 整秒。两段耗时都使用同一部手机的单调时钟。两段均无重传、`t1 − t0 ≤ 1000 ms`、`t3 − t2 ≤ 1000 ms`、手机期间无系统时间跳变，才进入短时精度判断。
3. 判为“校时已验证”须同时满足上面的计时条件、SetTime 回读合格、GetStatus 的 `time_state=02`，且 `abs(手表快照 UTC − 手机在 t3 的 UTC) ≤ 2 秒`。两边都按 UTC 秒比较，包括北京时间跨日的情况。若条件合格而差值超限，显示读回偏差并保留两端值。
4. 若超出低延迟窗口或发生重传，记录“延迟过大／待复核”。写后超时、IO_ERROR、回读不合法或断线，记录“校时结果待确认”。连接就绪后先用新 seq 查询当前时间；断线时先建新 session。仅当新查询表明仍需校时，才用当前时间发起新 SetTime。若查询已吻合，可显示“当前时间已核对”，保留原校时尝试的未确认或超窗口状态。

#### 基础协议验证条件

| 验收项目 | 操作与期望结果 |
| --- | --- |
| 身份与状态 | 新会话 seq=1 读 DeviceInfo，再读 GetStatus。核对真实 UID、编译版本、能力和状态。scope=00 的有效步数显示“累计步数”，有效的 0 可显示为 0 步。未支持或无效显示对应状态。 |
| 流解析 | 分片传一帧、连续传两帧、跨分片拆开 A5/5A、坏 CRC 帧后接好帧。接收方只交付完整有效帧，能继续解出后面的好帧。回包中旧会话、错误 cmd 或错误 seq 均不可完成当前请求。 |
| 最大帧边界 | 在帧编解码层用 128 字节载荷组成 145 字节帧，分段到达时仍可完整解析。长度字段为 129 的候选在收满 13 字节帧头后即拒绝，后续合法帧仍可解析。具体命令载荷长度另按命令规则校验。 |
| 校时成功与边界 | 按四步流程验证原秒和进 1 秒的应答均可接受。记录四个单调时刻、手机 UTC、SetTime 回读 UTC、新状态 UTC 和 time_state。检查 1000 ms、差 2 秒的边界，以及超出边界时的提示。 |
| 错误与去重 | 越界 UTC 返回 02，长度错误返回 01，两者都不写 RTC。丢弃首个 SetTime 成功应答，再发同一帧，期望重放相同应答且 RTC 只写一次。相同 seq 改内容返回 07，已过有效缓存的旧请求返回 08。用写入计数或固件跟踪核对执行次数。 |
| 断线与恢复 | 在 SetTime 已发、应答未到时主动断开。手机结束旧事务，重连后用新 session 查询身份和状态；记录此时 RTC 实值与界面结果。 |
| 请求残帧后重连 | 发送 SetTime 前半帧后断开，保留手表 UART 半帧。新会话按半帧恢复要求等待后发送 DeviceInfo，随后 GetStatus。记录旧 UART 最后一字节、候选失效和新帧起点；原残帧写 RTC 次数为 0。 |
| 部分应答后重传 | 让手机只收到 SetTime 应答前半帧，等应答超时和本地候选过期后重传完全相同的请求。确认收到完整缓存应答，RTC 写入次数为 1。 |
| 执行期间的重复与冲突 | 暂停 SetTime 的读回完成步骤，分别注入同 seq 原样副本、同 seq 改内容（重新算 CRC）、更大 seq 和新会话 DeviceInfo。核对合并、07、06、06；解除暂停后原应答按原 seq 发出且 RTC 只写一次。 |

以上为验证条件，不代表所有项已实机通过；软件、真实连接故障及App逻辑注入的结果边界见F06.md。后续变更须保持已确认报文字节与错误语义，公开示例不写真实UID。

抬腕识别、按键唤醒、超时熄屏、运动与PPG采样、低活动算法、低电滞回、STOP和唤醒恢复由手表端负责（F04/F05/F08/F09/F13/F14），手机端展示相关状态。本期手机端范围为Android本地应用及上述功能；新增远程控制项由双方另行确认。

### APP-04 D3参数读写扩展（2026-11-28，手表已实现，待手机负责人确认接入）

固件 `F06-P03-20261128-01`。沿用D3版本01、145字节上限、CRC和会话/序号规则，前三条命令及GetStatus的SESSION语义不变。当前Android的D3Identity严格拒绝bit9以上能力位，因此DeviceInfo继续返回0x1F；手机新入口显式探测GetSettings，旧固件返回03 UNSUPPORTED时禁用设置，不能把“设备连接成功”当作设置已支持。当前手机的DeviceSettings/WatchRepository为逻辑/离线模型，真表D3Command仍只有前三条；此处为手表侧已实现协议，尚非双方完成冻结或实机联调。

`GetSettings cmd=0x04`：请求N=0。成功响应N=27，payload[0]=00；其后26字节数据按下表解析（偏移从payload[1]开始计算，所有多字节数小端）：

| 数据偏移 | 字段 | 字节数与含义 |
| --- | --- | --- |
| 0 | schema | 1，固定1，独立于Flash载荷版本 |
| 1 | persisted_flags | 1，bit0一次性延时已有保存字段、bit1低活动配置已有保存字段，其余0；两位均1才是完整v3配置 |
| 2 | reserved | 2，均0 |
| 4 | generation | 4，参数槽代号；空白默认0，合法保存可按uint32回绕到0，结合persisted_flags区分 |
| 8 | reminder_delay_seconds | 2，一次性提醒延时配置；不是已ARMED到时目标 |
| 10 | activity_minutes | 2，低活动时长分钟 |
| 12 | activity_enabled | 1，严格0或1 |
| 13 | reserved | 1，0 |
| 14/16/18 | delay_min/max/step | 各2，当前30/300/30秒 |
| 20/22/24 | activity_min/max/step | 各2，当前5/120/5分钟 |

空白介质返回30秒、30分钟、低活动关闭及flags=0，不提前显示已保存。v1默认两个新属性、flags=0；v2使用已保存延时、低活动默认关闭/30分钟、flags=1；合法v3返回flags=3。加载失败或未知载荷返回错误，不将其当成默认值。存储加载未就绪返回04 NOT_READY，保存/重读忙返回06 BUSY。

`SetSettings cmd=0x05`：请求N=12，偏移0为schema=1、1为保留0、2为延时uint16、4为低活动分钟uint16、6为使能0/1、7为保留0、8为expected_generation uint32。两种配置在一笔双槽事务中提交，保留最新诊断计数；不扩展Flash载荷v3，不写入C结构体。非法长度01 BAD_LENGTH，版本/保留位/范围/步长/使能非法02 BAD_VALUE；与刚读代号不一致返回新增错误0B CONFIG_CONFLICT，手机应重读并提示用户核对，不能自动覆盖本地修改。

只有提交标记写入、Flash回读和完整属性/代号/原计数核对完成，才返回与GetSettings相同的27字节成功payload；入队不回复成功。旧缓存及原参数槽在失败时保留，未知目标槽拒绝覆盖。等待最长3000ms，超时返回0A TIMEOUT只结束协议等待，不取消可能仍进行的Flash事务；断连、丢包或超时都可能结果未知，应先用新序号GetSettings核对，禁止盲目重写。请求在执行中重传不再写Flash，完成后30秒内相同session/seq/载荷重放同一完整应答；同序号异载荷仍为07，旧序号08。重启不承诺跨重启去重。

手机接入顺序：真实串口就绪→DeviceInfo→GetSettings→编辑→带读到的generation发SetSettings→新seq GetSettings核对→再显示保存完成。保存失败不覆盖界面已提交值；保留“保存中/失败或结果待确认/已保存”状态。低活动新值由现有活动服务读取并应用；本地SET草稿仍可保持旧值，SAVED显示当前提交值，长按SOS重读会丢弃草稿。保存一次性延时不创建、取消或修改正在计时的提醒；不支持每日时分闹钟，手机离线DeviceSettings的alarmEnabled/alarmHour/alarmMinute不能据此发送或显示可用。15秒活动测试不作为正式配置上报或保存。

## 尚未冻结的扩展接口

现有DeviceInfo/GetStatus/SetTime及GetSettings/SetSettings的字节定义以上文为准，不再列作“待定义”。下列历史、事件及OTA只有逻辑需求，新增命令编号和样例由双方按对应任务确认：

| 逻辑接口 | 方向 | 请求/事件内容 | 应答/上报内容及约束 |
| --- | --- | --- | --- |
| 历史查询 `GetHistory` | 请求→分页应答 | 游标/起始记录、页大小；日期过滤是否由设备支持待定 | 记录唯一标识、类型、时间、值及单位/有效性、下一游标和结束标志；约定覆盖环形存储后游标失效行为，不能默默跳过 |
| 求助事件 `SafetyEvent` | 手表→手机 | 事件ID、来源（手动/跌倒）、发生时间及有效性、阶段（待确认/已发起/已取消等） | 手机按ID去重并更新阶段；断线期间是否存储、如何补报及去重生命周期待约定 |
| 接收确认 `EventAck` | 请求→应答 | 已收到的事件ID | 只证明手机收到设备事件，不证明用户拨号/短信发送或接收方送达；ACK与重传规则待冻结 |
| 升级开始 `OtaBegin` | 请求→应答 | 镜像目标硬件、版本、长度、整包CRC；镜像头格式待定 | 是否可升级、拒绝原因、支持片长和设备确认的接收偏移；设备端负责容量及兼容性判断 |
| 升级分片 `OtaChunk` | 请求→应答 | 本包偏移、实际数据长度和数据 | 设备确认的连续接收偏移/失败原因；重传重复包应可识别，片长受实际传输能力约束 |
| 升级查询 `OtaQuery` | 请求→应答 | 查询当前升级会话 | 当前镜像标识、状态、已确认偏移、错误；只有同一镜像才能续传，不能仅依据手机本地进度恢复 |
| 升级结束 `OtaFinish` | 请求→应答及重连查询 | 请求完整校验并进入升级流程 | 校验结果、是否进入重启/安装、失败原因；最终成功以重连后的设备版本和升级结果确认，传输100%不等于升级成功 |

手机端管理本地联系人、CSV保存分享和短信/拨号调用，手表负责离线提示；事件补报和去重生命周期另行确定。Flash历史已有递增ID和按ID读取API，但C记录载荷与物理ID分离，不代表已存在可用线上分页协议。

## 剩余协议与交付边界

公共帧、CRC算法、大小端、基础错误和参数范围已在上文实现，不重新改写为待确认。仍须共同确定历史分页/覆盖失效/过滤与去重，健康数值与质量/陈旧标识，求助事件ID/阶段/取消/ACK及跨重启补报，Boot/App分区、镜像兼容、OTA偏移/重传/中断恢复，以及配对/授权；CRC不提供身份认证。BLE吞吐、实际通知分片上限、后台/锁屏和完整UART恢复边界按对应真实测试判断，不把离线模型或页面存在当功能通过。

手机端交付可安装APK、可构建源码/版本、系统支持范围及未支持项；手表端交付对应固件、通道约束、已实现报文和可复算样例。每次联调注明APK及固件版本；顺序为连接/身份→状态/校时→提醒参数→历史/CSV→健康→SOS/跌倒→OTA。实现和验收边界以各项实际记录为准，不因源码存在将后续接口标完成。
