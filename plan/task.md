**当前交接状态：需求已整理，通信协议尚未冻结，代码尚为骨架。** `code/Application/android/`中七个Kotlin文件均未实现，也没有实际Android Gradle工程；手表端`ble_protocol`同样未实现。以下接口名称是便于双方讨论的逻辑名称，不是已实现的命令编号、JSON格式或可直接调用的API。手机端可先做页面、状态模型和模拟数据，真实收发须待下文协议项共同确认。

抬腕识别、按键唤醒、超时熄屏、运动与PPG采样、低活动算法、低电滞回、STOP和唤醒恢复均由手表端负责（F04/F05/F08/F09/F13/F14）。手机端只消费相关状态，不新增远程控制项。多组闹钟、重复周期、手机远程取消求助/重置步数/启动测量等未在现有范围中明确的控制，不作为已确认需求；若需要，先补充本节和接口约定。当前范围不要求账号登录、云端、iOS或自动发送短信。

## 手机与手表的接口清单

方向以手机为参照。表中字段为双方必须协商覆盖的信息，尚不是字节布局。除接口准备阶段外，手机端不依赖STM32内部函数或内存结构，不直接把C结构体当作通信数据。

| 逻辑接口 | 方向 | 请求/事件内容 | 应答/上报内容及约束 |
| --- | --- | --- | --- |
| 设备信息 `DeviceInfo` | 请求→应答 | 查询设备信息 | 稳定设备标识、硬件型号/版本、App固件版本、协议版本、支持能力；OTA另需镜像兼容与Boot能力信息，确切字段待冻结 |
| 当前状态 `GetStatus / StatusChanged` | 查询→应答；手表→手机 | 查询状态；是否周期订阅及其频率待定 | 时间与有效性、日期对应的步数、电池mV及估算%、心率bpm、估算血氧%、各测量有效性、更新时间；若要展示接触质量须增加质量状态定义，不能由手机猜测 |
| 校时 `SetTime` | 请求→应答 | UTC Unix秒（1970-01-01 00:00:00起点）；2026-11-07用户确定本地固定北京时间UTC+8，不使用夏令时 | 成功/失败及设备实际保存时间；本地显示、日期切换与按日步数统一使用UTC+8，不随手机时区变化 |
| 参数读取 `GetSettings` | 请求→应答 | 查询当前参数 | 定时提醒设置、低活动提醒时长及可支持范围/版本；支持启用开关、数量和默认值须共同确认 |
| 参数保存 `SetSettings` | 请求→应答 | 需要修改的提醒参数 | 参数是否合法、是否持久化成功、实际保存值；不能只依据BLE写入成功就判断参数保存成功 |
| 历史查询 `GetHistory` | 请求→分页应答 | 游标/起始记录、页大小；日期过滤是否由设备支持待定 | 记录唯一标识、类型、时间、值及单位/有效性、下一游标和结束标志；约定覆盖环形存储后游标失效行为，不能默默跳过 |
| 求助事件 `SafetyEvent` | 手表→手机 | 事件ID、来源（手动/跌倒）、发生时间及有效性、阶段（待确认/已发起/已取消等） | 手机按ID去重并更新阶段；断线期间是否存储、如何补报及去重生命周期待约定 |
| 接收确认 `EventAck` | 请求→应答 | 已收到的事件ID | 只证明手机收到设备事件，不证明用户拨号/短信发送或接收方送达；ACK与重传规则待冻结 |
| 升级开始 `OtaBegin` | 请求→应答 | 镜像目标硬件、版本、长度、整包CRC；镜像头格式待定 | 是否可升级、拒绝原因、支持片长和设备确认的接收偏移；设备端负责容量及兼容性判断 |
| 升级分片 `OtaChunk` | 请求→应答 | 本包偏移、实际数据长度和数据 | 设备确认的连续接收偏移/失败原因；重传重复包应可识别，片长受实际传输能力约束 |
| 升级查询 `OtaQuery` | 请求→应答 | 查询当前升级会话 | 当前镜像标识、状态、已确认偏移、错误；只有同一镜像才能续传，不能仅依据手机本地进度恢复 |
| 升级结束 `OtaFinish` | 请求→应答及重连查询 | 请求完整校验并进入升级流程 | 校验结果、是否进入重启/安装、失败原因；最终成功以重连后的设备版本和升级结果确认，传输100%不等于升级成功 |

手机本地联系人、CSV保存分享、短信/拨号调用属于手机内部接口，不经BLE上传联系人或伪造送达回执。手表离线能完成本地提示；手机未连接时不能保证实时求助，恢复连接后的事件补报行为须按协议确认。

| 提醒参数 | 定时提醒是单次时间点还是其他形式、允许数量、启停/取消语义；低活动时长单位、上下限、默认值；不得各端自行增加不兼容参数 | 项目负责人确认范围，双方落实 |

| 求助状态 | 明确事件ID宽度与跨重启唯一性、阶段转换、取消顺序、重传/补报/确认；手机后台、锁屏和断线情况下能否收到与提醒须真实验证，不承诺必达 | 双方联合实机验证 |
| OTA与访问控制 | 明确镜像格式/版本兼容、最大长度、续传标识、分片及偏移、失败恢复、升级触发和实际结果；明确设备配对/授权方式及谁可改设置或升级，不将CRC当作授权 | 手表端提供Boot/App约束，双方共同确认 |
| Android工程 | 手机端负责人确定包名、最低/目标系统版本、构建工具版本及目标机型，交付可构建源码与APK；权限、后台连接、系统短信/拨号及文件分享按实际支持系统实现并验收 | 手机端负责人 |

当前函数签名如`ble_protocol_encode(type, sequence, payload, ...)`、`ota_begin(size, crc)`仅是手表内部骨架，不能证明上表协议已实现。逻辑接口增减或字段冻结继续更新本节，不另立相互冲突的协议说明。

## 双方交付与联调边界

手机端负责人交付Android工程、可安装APK、对应源码版本、支持的系统范围及尚未支持的接口；手表端提供对应固件版本、真实BLE通道参数、双方确认的帧与载荷定义、可复算的收发样例和功能状态。样例作为本节正式接口说明维护，不另留临时测试报告。

建议联调顺序：设备连接与信息查询 → 状态和校时 → 提醒参数 → 历史和CSV → 健康状态 → SOS/跌倒 → OTA。各接口先确认正常及失败应答，再验收断线/重连和重复消息；手机端可提前独立完成UI与本地功能，不据此宣称整机联调通过。每次联调须对应明确的APK与固件版本，任务状态仍由原计划表维护。
